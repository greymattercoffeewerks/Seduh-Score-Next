## Throwdown redemption round (TD.3) · 4.32.0 · 2026-11-27

**Status: built on `claude/td3-redemption`, NOT merged and NOT in the cloud (a live Throwdown ran on 27 Nov: no deploy, no cloud database change).** Migration `20261201100000_td_redemption.sql` is new and unpushed. Owner decisions of 27 Nov are spec section 14 (local): groups drawn randomly, several redemption rounds, a brewer can come back more than once, a new page shows the redemption competitors.

- **The module** (`redemption`, key `throwdown_redemption`, Per-event and up, in the registry on both sides): setup is exactly `{ group_size 2..4 (3), cap (0 = none), feed [main round numbers 1..4] }`, stored by `td_save_settings`; off stores nothing. After a main round the organiser ticked, the losers (active only; a bye has no loser) are drawn at random in the database into groups (`app.td_group_sizes`: ceil(pool / size) groups, as even as possible, never one brewer alone, so with groups of 2 and an odd pool one group is a three). Each group is a pool match (the 2..4 slots TD.1 reserved); nothing in the match, slot or vote tables changed shape. A round only follows a main round that leaves MORE THAN FOUR winners, and only with two brewers to draw; otherwise the bracket goes straight on (no trace).
- **Voting.** A group is the same table, view and functions as a pair: strictly the most votes wins. When every judge is in and the top is shared (a three-way 1-1-1 included), ONE tie-break vote opens and `td_cast_vote` refuses it for a brewer who is not in the tie (`td_tiebreak_slot`; a pair is unchanged). The console disables Vote for the others.
- **The way back.** When every group is decided, `td_advance` builds the next main round from the feeding round's winners then the group winners (the cap keeps the group winners with the most votes, ties by group order: an ASSUMPTION for the owner). Several redemption rounds work (one per ticked feeding round); nothing blocks a returning brewer. Everything is derived and idempotent (a second Continue creates nothing).
- **Pair assumption in `td_advance` fixed** (ROADMAP "Pool matches (TD.3)"): the latest round is the latest main OR redemption round, losers come from the decided winner's slot for any number of slots, and the 3rd place logic only reads a main round of two matches. `td_reopen_match` and `reopen.js` treat a redemption match like a main one (undo while no later round has a tap).
- **Surfaces, each tested with a group in it and with the module off** (`redemptionSurfaces.test.js`): a new console page `#/events/:id/throwdown/redemption` (who is in, the groups, the winner; reached by a link on Matches that exists only once a redemption round does; no tab); group vote cards; run sheet (a phase per redemption round); phone ("Group 1: A, B, C", votes most first); projector (a group Up next page, "the groups" round page, latest result); results page ("Group 1: A, B and C"); the match-log CSV gains Competitor C/D and Votes C/D ONLY when a group exists (it dropped a third brewer before the test caught it); published places place a revived brewer once, by the last main round lost (a loser of Round 1 who came back and lost later was listed twice). A group is not in the published knockout record (owner to decide).
- **Owner answers, 27 Nov:** build 1 v 1 first (the setup offers pairs only; the database and helpers still know sizes 2 to 4, tested, so bigger groups come later without a migration; an odd pool still leaves one group of three); the cap rule is fine (most votes, ties by group order; a walkover winner has no votes so ranks last); store the shuffle seed: done as `td_rounds.draw_seed`, a draw code the database makes, the pool ordered by `md5(code || competitor id)`, shown on the Redemption page, replayable (pgTAP `095`); the page layout is fine.
- **Still open:** "strict majority" for a group of 3 or 4 (built as strictly the most votes, matters only when bigger groups ship); a "redemption round is drawn" projector moment (not built); whether a group result counts on a Seduh ID profile (it does not); (owner, 27 Nov, both OK for now: an odd pool leaves one group of three; the next round pairs the feeding round's winners in order then the revived, so the last group's winner gets any bye and a rematch with a just-beaten brewer is possible); a reopen of a feeding-round match redraws the groups with a new code.
- **Tests.** pgTAP `095` (123 checks; `072`/`091` edited for the registry), `redemption.test.js`, `redemptionSurfaces.test.js`, `eventScreen.redemption.test.js`, Playwright `throwdown-redemption.spec.js` (12 players, groups of 3, tie-break, return into the quarter-finals on the real local stack).
