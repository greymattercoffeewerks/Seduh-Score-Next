## My Seduh ID forms: boxes side by side line up · 4.20.1 · 2026-11-19

**Status: NOT FINAL** until the PR is merged and reviewed. Owner-reported 2026-11-19 (screenshot of "Add an entry" at desktop width). **Version 4.20.1 (patch: a fix).**

- **What was wrong.** From 900px the entry and course forms in My Seduh ID are two columns. A field stacks label, hint, box and message, so a field with a hint ("From 1980 to this year.") put its box 20px below a neighbour without one ("What you did"), and the course form's Level box 34px below Note. The "What you did" dropdown was also 54px tall against 44px for the text boxes.
- **Fix** (`src/marketing/me.css`, inside the 900px query): each field takes four rows of the form grid through `subgrid` (label, hint, box, message), so side-by-side boxes share a top edge whatever hints there are. The form's own row gap would have opened between those rows too (an empty hint row would add a gap), so the spacing is margins instead; a field without a hint keeps 8px between label and box, and the rows land where they did before. The dropdown is held to the text boxes' 44px (`.me-form-grid select.claim-input`). Below 900px nothing changes but the dropdown height.
- **Tests.** Playwright `seduh-my-seduh-id-live` (entry form at 1280px: each pair shares top and height, still after an error message, label-to-box gap without a hint) and `seduh-courses-live` (course form: title/provider and year/valid-until share top and height, level/note share a top). Both fail without the fix (20px and 34px) and pass with it; the full My Seduh ID, courses and not-mine specs pass (11), as do `src/marketing` unit tests (666).

## Local database: lock and per-worktree pgTAP · tooling, no version · 2026-11-18

**Status: NOT FINAL** until the review line below is filled and the PR is merged. Branch `claude/db-test-lock`. No §14 task ID: owner request after a pgTAP run sat for 20+ minutes. **No version bump:** tooling, docs and local config only (`docs/versioning.md`: tooling-only changes pass the gate).

- **Why.** Every worktree, and so every parallel Claude session, shares one local Supabase stack, and `supabase test db` / `db reset` only use its `postgres` database. On 2026-11-18 the Seduh ID C5 session ran pgTAP against a database another session (BTC void cups) had just reset to its own schema; its run was killed by a timeout in `029_btc_seeding_tiebreak`, but the database kept running the killed query for about 20 minutes with its transaction open, and the next runs queued behind its locks.
- **The lock** (`tools/db-lock.mjs`, `npm run db:lock`). A reader/writer lock kept as files in `.git/seduh-db-lock/`, which every worktree shares. `npm run db:reset` now takes the exclusive hold and waits for pgTAP runs in progress; Playwright should be wrapped the same way (`npm run db:lock -- run -- npm run test:e2e`). A holder whose process is gone, or past its age cap, is cleared by the next caller. Not a Postgres advisory lock: a reset drops the database that would hold it.
- **Per-worktree pgTAP** (`tools/db-test.mjs`, `npm run db:test`). Each worktree tests in its own database, `seduh_wt_<worktree>`, in the same container: a clean Supabase base (dumped once per Postgres image from a throwaway second project with no migrations) plus this worktree's migrations and seed, applied with psql. A fingerprint skips the rebuild while the migrations are unchanged. The database gets `statement_timeout` 120s and `lock_timeout` 30s, a run is stopped after 15 minutes, and a leftover query from a killed run is cleared first. The old behaviour is `npm run db:test:shared` (under the lock). CI is unchanged.
- **A trap found while building it.** `supabase db reset --db-url postgresql://...@127.0.0.1:54422/<another database>` is treated as LOCAL: the CLI reset the shared `postgres` database and restarted the stack (no session was mid-run; the shared database was left on `dev`'s schema). Recorded as a rule in `CLAUDE.md`.
- **Memory.** `supabase/config.toml`: `[analytics] enabled = false` (the analytics container used about 550 MB of Docker's 7.4 GB and its log shipper was in a restart loop). Takes effect on the next `supabase stop` / `start`. A per-worktree database is about 41 MB on disk; `npm run db:test -- --prune` drops those of deleted worktrees.
- **Verified.** Full `npm run db:test` in its own database: 88 files, 5,630 tests, PASS (same count as CI); first run about 4 minutes including the base and database build, a repeat run of two files 10 s with the rebuild skipped. Lock: an exclusive hold waited for a shared one (7 s) and a shared one for an exclusive one (4 s); a holder killed with `taskkill /F` was shown stale and cleared. The shared `postgres` database was not touched by any of these runs. The Windows argument quoting bug in the wrapper was found by these runs and fixed.
- **Reviews.** `code-reviewer`, one round: 2 Important, 5 Nits, all fixed. Important 1: a hold's age was counted from when it started WAITING, so a run that had queued could be cleared as stale mid-run (fixed: the time is set when the hold is taken). Important 2, class "writer slot removed by a non-owner": `release()` and the stale-clearer deleted `writer/` without checking it was still theirs (fixed: every hold carries a token; the slot is renamed to a unique name, its owner checked after the rename and put back if it was someone else's; the writer re-checks ownership before proceeding). Nits fixed: a base whose auth/storage set-up had not finished could be cached (now waits until both migration counts hold still, else fails); a concurrent first base build could crash on a missing pid file; `--timeout-mins` above the shared hold's cap (now 1 to 25); a wrapper killed without its child freed the lock (the child pid is recorded and counts); a stray empty file from a test command. The independent fresh-context check was not run as a separate agent: both Important findings were confirmed by re-reading the code, and the ownership fix by a test where the slot changes owner under a holder (its release leaves it alone). Re-verified after the fixes: the lock cases above, and a full rebuild from a deleted base (base 45 s, worktree database 4.6 s) with 88 files, 5,630 tests, PASS.
- **Local timing, for the record.** pgTAP itself takes about 165 s on this machine against 23 s in CI (Docker on Windows); a follow-up could look at that separately.
- **Seen in passing.** The C5 discovery branch (merged first, #505) and the BTC void-cup branch both used migration version `20261125100000`; the void-cup branch renumbered to `20261125110000` (done in #508).
